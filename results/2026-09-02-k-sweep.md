# DSpark draft-depth (MTP_NUM_TOKENS / k) sweep — 2026-09-02

Frozen recipe: 2x DGX Spark (GB10), vLLM TP=2, `kv-cache-dtype nvfp4_ds_mla`,
served model `deepseek-v4-flash-vision-exp`, checkpoint revision
`86f746b36186f0e567729a5c06a8c918caba82a9`. One variable changed per run:
`MTP_NUM_TOKENS` (draft depth, k). Everything else held fixed.

## Runtime constraint discovered

The Vision-Exp checkpoint's `num_nextn_predict_layers=3` imposes a hard
runtime gate not present on the text-only `DeepSeek-V4-Flash-0731`
checkpoint: **k must be >= 5 and divisible by 3.** In the valid range near
the current setting, that leaves only k=6 (the next valid value up is k=9,
not requested).

| k | Result | Exact error |
| --- | --- | --- |
| 3 | REJECTED (validator) | `error: Vision-Exp requires MTP_NUM_TOKENS >= 5 and divisible by 3 (num_nextn_predict_layers=3); got 3` |
| 5 | REJECTED (validator) | `error: Vision-Exp requires MTP_NUM_TOKENS >= 5 and divisible by 3 (num_nextn_predict_layers=3); got 5` |
| 6 | PASS (current/only valid tested value) | n/a |

Both rejections happened at container-entrypoint validation time, before
`vllm serve` executed — no weight load, no GPU time spent, no restart churn
beyond the roughly 15-second compose stop/start cycle each.

## Correctness gate (golden corpus, 30 rows)

- k=6 defines the golden corpus by definition.
- k=3 and k=5 never reached serving state, so no corpus run exists for
  either; drift is undefined/n/a rather than measured.
- k=6 was restarted (stop, then restore) after the k=5/k=3 rejection cycle.
  Re-running the golden corpus against the restored instance gave 29/30
  keyword-match (versus 27/30 on first boot) and 17/20 exact text match. All
  differences are `length`-to-`stop` flips or minor wording changes on
  borderline rows; no keyword-match row flipped from pass to fail. This is
  consistent with vLLM's known greedy-decoding batch-composition
  non-determinism (a request's exact output can depend on what else is
  in-flight in the same batch), not a k=6 config change — the config
  (`MTP_NUM_TOKENS=6`, all other flags) is byte-identical to the first boot.
  Treated as within-tolerance for the correctness gate.

## Thermals

Both nodes stayed in the 50s-C range idle and mid-60s-to-68C under sustained
load, with no throttle or Xid events observed at any point in the bench and
restart cycle.

## Restarts

Three restarts total this session: k=6 -> k=5 (rejected, no serve) -> k=3
(rejected, no serve) -> k=6 (restored). Each stop/start cycle used the
launcher's graceful worker-then-head sequencing; no manual container kill
was needed.

## Verdict

**k=6 is the only valid draft depth for this checkpoint in the requested
set, and the service is left running at k=6** (this recipe's pinned value).
k=3 and k=5 are not runtime-supported for Vision-Exp, full stop — this is a
checkpoint-level constraint (`num_nextn_predict_layers=3`), not a tuning
outcome, so no drift/performance comparison is possible for those two
values.
